Trước hết phát hiện **có hai dialog gần như trùng nhau**: `PickIssueDialog` (relations, sub-task) và
`PickTaskDialog` (roadmap — đúng cái trong ảnh chụp). Làm tính năng hai lần thì chắc chắn lại lệch

riêng của roadmap: chấm trạng thái, dòng "Linked to …", câu cảnh báo "linking moves it", và lệnh ghi

**Gốc của yêu cầu "thể hiện hierarchy"**: `GET /issues?parentId=…` chỉ trả **một tầng**. Nên mọi chỗ
muốn nguyên cụm cây đều phải tự fan-out từng dòng — và vì đắt, không chỗ nào làm. Viết một lớp dùng
chung `features/issues/issueTree.ts`:
- `useIssueDescendants` — đi xuống từng tầng trong **một** `queryFn` (`MAX_DEPTH = 5`, mỗi tầng
  `limit` 100 vì `PaginationDto` chặn ở 100 — đặt 200 là API trả 400), tập `seen` vừa khử trùng lặp
  vừa cắt vòng lặp.
- `toIssueTree` — xếp tập phẳng thành thứ tự cây kèm `depth`; **cha không nằm trong tập thì coi là
  gốc**, nên không dòng nào biến mất chỉ vì cha ở chỗ khác.
- `subtreeIds` — vừa trả lời "tick cái này thì kéo theo những cái nào", vừa trả lời "cái này **không**
  được chuyển xuống dưới cái nào". Cùng một tập, vì đưa một issue xuống dưới con cháu của chính nó
  chính là cách tạo vòng.
- `rootsOf` — phần ngọn của một tập.

Cache của nó cố tình đặt key `['issues', 'descendants', roots]` và trả `{ items }`: đúng prefix mà
`makeIssueHooks` invalidate (sửa/xoá là dòng cháu cũng refresh), và đúng shape mà bản cập nhật lạc
quan của `setStatus` mong đợi (trả mảng trần là nó `old.items.map` → nổ).

**Picker**: thêm `multiple` → hàng có checkbox + nút "Link (N)". Mỗi kết quả tìm kiếm được vẽ kèm
**con cháu của nó** (kể cả những đứa không khớp từ khoá), tick cha là tick cả nhánh; bỏ tick lẻ thì

Chỗ **dễ sai nhất** nằm ở phía ghi: `onPick` trả `{ id, parentId }[]`, và host ghi `parentId` **chỉ

**List sub-tasks** (`SubtaskSection`) giờ là cây thật: dòng cháu thụt vào theo `depth`, mỗi dòng có
Select **Parent** — danh sách chọn loại trừ chính nhánh của nó (chặn vòng ngay từ UI), đỉnh danh sách

**Vùng Bugs**: thêm `separateBugs`, **chỉ bật ở `TaskPanel`**. Bug xuống list riêng dưới sub-tasks và

**Một lỗ hổng backend lộ ra khi làm việc này**: `PATCH /issues/:id` xưa nay nhận `parentId` bất kỳ,

### 7b. `[No parent]` trên breadcrumb

Fen đề xuất: chưa có cha thì để một khe `[No parent]` ngay giữa breadcrumb, đúng chỗ mà cha sẽ xuất
hiện. Tôi nêu ba cái giá trước khi làm — breadcrumb là dãy *nơi chốn* mà cái này là cái nút; crumbs
render bên trong `<h1>` nên nó thành một phần tên trang; và nó biến mất đúng lúc muốn *đổi* cha, nên
Properties vẫn phải tồn tại song song. Fen vẫn chọn phương án chữ, luôn hiện — quyết định của product
owner, làm theo.

- **`PageCrumb` nới ra**: `to` thành optional, thêm `onClick`. Có `to` → `<Link>`; có `onClick` →
  `<button>` viền **đứt nét** — crumb duy nhất không điều hướng thì không nên trông giống crumb điều
  hướng. Class dùng chung (`CRUMB`) để hai dạng nằm cùng baseline.
- **`useIssueCrumbParent(kind, issue, onSetParent?)`**: có cha → crumb link như cũ; chưa có cha **và**
  caller truyền `onSetParent` → crumb `No parent`. Không truyền thì không hiện — khe không điền được
  chỉ là rác, nên `BugDetailPage`/`TaskDetailPage` chỉ truyền khi `canEditDelivery`. Chỉ render khi
  `issue` đã load, không thì mỗi lần mở trang khe rỗng sẽ nháy lên rồi mới bị cha thật thay thế.
- **`useParentPicker.tsx`** (mới) tách từ `ParentPropField`: state dialog + exclude con cháu + lệnh
  ghi + toast lỗi, gói một chỗ vì giờ có **hai** nơi mở cùng một picker (dòng Properties và khe
  breadcrumb). `ParentPropField` giờ chỉ còn phần hiển thị. Hai nơi mỗi nơi một instance là cố ý:
  peek drawer và Inbox mount `BugDetail` mà **không có** PageHeader nào, nên dòng Properties phải tự
  đứng được.
- Phân vai rõ: **breadcrumb chỉ lo set lần đầu**, **Properties lo set/đổi/gỡ**.

Kiểm chứng: `tsc --noEmit` sạch, `vite build` pass (18.74s). Tiêu đề tab không bị ảnh hưởng —
`usePageTitle(title)` chỉ lấy title, không lấy crumbs.

## 8. "search parent issue ko tìm được backlog item (RM-7VBD8CR)"

item". Nhưng nó đang dính **đúng cái lỗ vừa vá cho parent**:

- `BugDetail` **không có dòng nào**, dù bug vẫn mang `roadmapItemId` (chính là thứ khối "Bugs" của
  `separateBugs` liệt kê ra).

**Đã làm**:
- **`features/roadmaps/useBacklogLink.ts`** (mới) — một nguồn duy nhất cho danh sách chọn + 4 field
  phải ghi kèm nhau. Nhãn option **dẫn đầu bằng `RM-…`** vì Combobox lọc theo chuỗi nhãn — ref phải
  *nằm trong* nhãn thì dán `RM-7VBD8CR` mới ra. `roadmapItemLabel` sinh ra **giống hệt**

## Sortable issue IDs

**Prompt:** hiện tại https://team.linkadz.store/issues/BUG-ESP4F4T các id của các task or backlog nó đang gen tùm lum, như jira, trello thì các ticket khi được tạo ra được đánh số hay thứ tự, tao muốn có thể sort theo ID, thì mày có thể cải thiện id này có thể sort được không, các ticket mới được tạo ra tiếp theo còn các ticket cũ vẫn giữ nguyên

- Legacy rows are never written to; they sort as one `createdAt`-ordered block.

## Sortable issue IDs — implementation (branch `feat/sortable-issue-ids`, 20 commits)

Executed the plan task-by-task with a fresh implementer per task and a review after each.
Backend: 34 suites / 277 tests pass; backend + frontend typechecks clean; frontend builds.

### Deploy runbook — the backfill runs as part of deploy, before traffic

No local database was available (docker daemon down), so nothing on this branch has ever been
run. The product owner's decision: **the backfill is a deploy step, not a follow-up.** Run it
after the code is up and before the workspace takes traffic, in exactly this order.

**Why the order matters:** a team that mints a ticket before it has a prefix draws from the
workspace-wide `TSK-`/`BUG-` sequence instead of its own, so its list ends up with a permanently
misordered block of `TSK-*`/`BUG-*` refs sitting among its `ENG-*` ones — and those refs are
already printed in commits and comments, so they can never be renumbered.

1. **Deploy the code.**
2. **Boot the app once against the database.** This is what creates the two new indexes:
   `{tenantId, refPrefix, refSeq, createdAt, _id}` on `issues` (non-sparse, built against the
   whole collection) and the unique partial `{tenantId, refPrefix}` on `teams`.
3. **Verify the indexes actually exist — do not assume.** An index build failure is *silent* in
   Mongoose (it swallows `Model.init()`), which is why bootstrap now logs one explicitly; read
   the log for `MongoIndexes`, and then confirm in the shell:

   ```js
   db.teams.getIndexes()    // expect a unique partial index on { tenantId: 1, refPrefix: 1 }
   db.issues.getIndexes()   // expect { tenantId: 1, refPrefix: 1, refSeq: 1, createdAt: 1, _id: 1 }
   ```

   Without the `teams` one, two teams can take the same prefix and mint the same refs. The
   backfill refuses to `--apply` without it, but the running app has no such guard — so if it
   is missing, fix it before step 4 rather than proceeding.
4. **Dry run the backfill, per tenant.** `npm run backfill:team-ref-prefix -- --tenant <id>`.
   Read the two numbers it prints per team: `issues=` is how much history the prefix will
   describe, `counter=` must normally be 0 — a non-zero counter means the team's first ticket
   will not be `-1`. A prefix freezes the moment its team mints a ticket, so this is the last
   moment a bad auto-derivation can be corrected.
5. **Apply, per tenant.** Same command plus `--apply`. It reports "wrote N of M"; a per-team
   write failure is counted and the run continues, exiting non-zero. Re-run the dry run and
   confirm "would assign 0".
6. **Open traffic.**

Omitting `--tenant` runs the whole shared database in one pass. Only do that on a single-tenant
install.

### Behaviour changes worth telling the team about

- **Lowercase refs in commit messages no longer create code links.** `eng-14` and `tsk-6hcuhkx`
  used to link; now only uppercase does. Unavoidable once prefixes became open-ended, else
  `well-known` parses as a ref. Approved.
- **Ticket numbers can jump.** A workspace carrying legacy sequential refs galloping past them
  can land the next ticket at e.g. `BUG-1001` rather than `BUG-501`. Correct by design.
- **Sorting is within status groups**, not page-wide — the list view keeps its grouping.
- **Sorting is opt-in.** No list applies a sort until the user picks one, so a fresh list is
  byte-for-byte the ordering it had before this branch. A default ID sort would have been
  actively harmful: the page is capped at 100 rows with no pagination and the ID sort leads on
  `refPrefix`, so on the team-less routes it returned 100 rows of the last team alphabetically
  and hid the others entirely.
- **Prefix rejections are now translated.** The API sends a `code`
  (`TEAM_PREFIX_TAKEN` / `TEAM_PREFIX_FROZEN` / `REF_PREFIX_INVALID` / `REF_PREFIX_RESERVED`)
  beside its English message; the frontend maps each to its own string and falls back to the
  message for any code it doesn't know.

## Production findings and fixes (same day)

The database this app runs against (`internal_product_os`) is **live**, not local dev.

### Pre-existing production bug found while testing — now fixed

`tenants.slug` carried a `unique + sparse` index. `sparse` only excludes documents where the
field is ABSENT; the schema declares `slug: { default: null }`, so every tenant gets an explicit
null, all of them enter the index, and **only one slug-less tenant can ever exist**. Observed:
one workspace registered fine, the next returned 500 with
`E11000 … index: slug_1 dup key: { slug: null }`. Both creation paths were affected — self-serve
register (never passes a slug) and the platform console (slug optional).

Fixed by replacing `sparse` with `partialFilterExpression: { slug: { $type: 'string' } }` — the
same pattern this branch uses for `{tenantId, refPrefix}`.

**Mongoose will not redefine an index that already exists**, so the live `slug_1` must be dropped
before the correct one can be created. Migration script: `backend/scripts/drop-tenant-slug-index.ts`
(`npm run migrate:tenant-slug-index`, `:apply` to act). It classifies the existing index as
broken / correct / absent / unknown and refuses to drop anything it does not recognise.

**Run order:** deploy code → dry run → apply → **restart the API promptly** (between the drop and
the restart there is no uniqueness constraint on slugs at all) → verify with
`db.tenants.getIndexes()` → smoke test two slug-less tenants.
Rollback: `db.tenants.createIndex({slug:1},{unique:true,sparse:true})`.

### Two other fixes

- **Exact ref search.** Typing `ENG-1` also matched `ENG-10`…`ENG-19` and buried the exact row.
  A `PREFIX-digits` search now floats the exact `shortId` to the top; any other text takes the
  untouched code path. An explicit user sort still wins over the rank.
- **`GET /v1/teams` N+1.** The prefix-lock resolver did one counter read per team on the endpoint
  the frontend hits on nearly every page. Now a single `$in` via `CounterService.currentMany`.
