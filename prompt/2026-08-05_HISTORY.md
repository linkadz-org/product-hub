## 4. PR link theo commit bên trong, và hiện destination branch
> tôi muốn dù nội dung PR có taskid hay không, chỉ cần PR đó có commit của task id thì nó sẽ hiện
> trong task, vậy làm được không? đọc cả vào commits của PR nữa
> và sửa giao diện cho nó hiện destination branch nữa, dest branch = môi trường dev/main

**Ràng buộc**: payload `pull_request` của GitHub **không** chứa danh sách commit (chỉ có *số lượng*).
Muốn đọc thật thì phải gọi REST API `GET /repos/…/pulls/{n}/commits` bằng token đọc được repo — phá
đúng cái tính chất đã hứa với product owner ở mục "phần quyền mình tính sao": không token, không
scope, mình không đọc code của họ.

**Cách làm, không cần thêm quyền**: các `push` event đã mang sẵn commit của nhánh đó và đã ghi
`code_links`. Nên PR không hỏi GitHub, mà hỏi lại chính mình — nhánh head là chỗ join: *việc đã push
lên nhánh đó chính là việc nằm trong PR*.

- `ICodeLinkRepository.findSubjectsForBranch(tenantId, repo, branch)` — các subject mà commit trên
  nhánh đó đang trỏ tới. Thêm index `{tenantId, repo, branch, kind}`.
- `ICodeLinkRepository.findSubjectsForExternalId(...)` — subject mà chính PR này *đã* link. Cần vì
  sau khi merge, commit được giao lại dưới `dev` (nhánh head bị xoá), nên một PR chỉ match qua commit
  sẽ mất dấu và kẹt ở trạng thái "Open" mãi. Hàm này trả kèm `matchedBy` cũ để đổi state không ghi đè
  lý do link tồn tại.
- `CodeLinkMatchedBy.COMMIT` — nhãn cho link đến từ commit trong PR chứ không từ chữ của PR.
- `MAX_BRANCH_SUBJECTS = 50` — quy tắc "PR chứa việc của nhánh head" đúng với feature branch, sai với
  nhánh sống lâu: PR release `dev → main` có sau lưng **mọi** task từng merge vào `dev`. Quá ngưỡng
  thì nhánh rõ ràng không còn là một đơn vị công việc, chỉ tính chữ của PR. (Ban đầu để 20, product
  owner nâng lên 50 sau khi thấy dữ liệu thật.)

**Destination branch**: thêm `baseBranch` (record → schema → DTO → mapper → `CodeLinkDto`). PR lưu
`pr.base.ref`; commit để rỗng vì `branch` của nó đã là nơi code nằm rồi. UI thêm `BranchRef`: PR hiện
`head → base`, luôn giữ base (đó là môi trường — `dev`/`main`), nhánh nguồn ẩn dưới `md`.

**Kiểm chứng**: `tsc --noEmit` sạch cả hai phía, `vite build` pass, `jest` 132/132 pass — 4 test mới:
lưu base branch, PR không có ref trong title vẫn link qua commit, PR merged vẫn cập nhật state sau khi
commit chuyển sang `dev`, và ngưỡng 50/51 của nhánh sống lâu.

## 6. Trạng thái CI/CD của CircleCI hiện lên panel Development
> giờ cái circleCI job nó không report lên cho github nữa hay sao á, lúc trước tui nhớ có thấy chấm vàng
> không, cái này là PR vào dev á, job lấy code từ dev vào chạy, nó không hiện circle ci chạy lên đây
> huhu tui chỉ muốn job chạy done báo về productos của tui thôi
> ê mà tui vào github check ko có như ban đầu tui nói, fen làm vậy rồi tui biết setup sao nhỉ

**Chẩn đoán trước, sửa sau.** PR #139 của `linkadz-portal-v2` hiện "Checks 0", nhưng CircleCI vẫn
chạy bình thường — kiểm chứng bằng GitHub API: commit head `e91664c` (nhánh `dev-felix`) có 0 status,
còn merge commit `44b5638` (trên `dev`) có 2 status `success`. Nguyên nhân nằm ở
`linkadz-devops/.circleci/linkadz-portal-v2.yml`: trigger là **push** + `filters: branches: only: dev`,
nên push lên nhánh feature sinh pipeline rỗng. Bản v1 (`linkadz-portal.yml`) dùng
`when: equal: [dev, << pipeline.event.github.pull_request.base.ref >>]` — trigger theo pull_request
event nên pipeline gắn vào commit head của PR, đó mới là "chấm vàng" ngày xưa. Việc job `checkout dev`
giống hệt nhau ở cả hai bản, không liên quan.

**Chốt hướng**: không đụng vào CircleCI. GitHub đã relay sẵn commit status qua webhook — chỉ cần
ProductOS xử lý thêm event `status`.

**Backend**: `GitHubEvent.STATUS` + `GitHubStatusPayload`; `CodeLinkCiState` (giữ nguyên 4 state của
GitHub — `pending` là chấm vàng board cần, `failure` khác `error` khi quyết định có retry không);
5 field `ci*` xuống schema/record/DTO/mapper; port `markCi` dùng `updateMany` nên một PR đóng 3 bug
thì cả 3 cùng được đánh dấu.

**Chỗ khó là status không bao giờ rơi đúng nơi có link.** CircleCI build `dev`, nên status gắn vào
*merge commit* — mà message của nó không nhắc tên issue nào. Cầu nối là số PR trong message:
`mergedPullRequestNumber` đọc cả `Merge pull request #139 from …` lẫn `title (#139)` của squash, ra
`pr-139` = đúng `externalId` đang lưu. Rebase merge không viết số nào, nên fallback là khớp `sha`.
Không khớp gì cả là chuyện thường (đa số commit chẳng thuộc issue nào) → no-op, vẫn trả 200.
`markCi` chặn theo `ciAt` vì GitHub không đảm bảo thứ tự delivery — `pending` về sau `success` không
được kéo chip vàng trở lại.

**UI**: `CiChip` trong `CodeLinksSection` hiện `✓ dev` — lấy tên **môi trường** làm chữ chính vì câu
người đọc đang hỏi là "fix của tôi lên dev chưa", không phải `ci/circleci: deploy-2`; tên job và thời
điểm nằm trong tooltip. Màu theo palette GitHub, cùng ngoại lệ với chip PR state.

**Setup thủ công** (product owner tự làm, không có trong code): GitHub → repo → Settings → Webhooks →
webhook của ProductOS → *Let me select individual events* → tick thêm **Statuses**. Mặc định webhook
chỉ đăng ký `push` + `pull_request`, đó là lý do vào GitHub check chưa thấy gì.

**Kiểm chứng**: `tsc --noEmit` sạch cả hai phía, `vite build` pass, `jest` 49/49 ở module integrations
— 7 test mới: stamp PR từ merge commit, đọc được squash merge, một PR đóng nhiều subject, fallback
sang sha, commit không ai claim, state lạ bị bỏ qua, và `pending` giữ được để chip đi vàng.
